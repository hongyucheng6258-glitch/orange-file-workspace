项目概况

Orange 是一个 本地优先、Windows 优先的桌面工作台，将文件管理、知识页面、代码项目、内置终端、全盘搜索和系统工具整合到单一界面。

核心功能覆盖

已实现

  • 文件管理：托管/外部模式、目录浏览、缩略图、批处理、哈希校验、原生拖出
  • 页面编辑：Tiptap 富文本、图片、表格、任务列表、页面树、草稿恢复
  • 代码项目：目录导入、文件树、CodeMirror 编辑、大文件保护、外部修改冲突检测

  • Web 预览：端口探测、进程归属校验、启动后自动打开
  • 内置终端：多标签、Shell 枚举、输入/尺寸控制、主题、命令历史
  • 混合搜索：资源库 + Windows Search + 后台全盘索引 + 应用索引
  • 数据安全：回收站、完整/元数据备份、恢复预检、目录迁移
  • 系统工具：硬件监控、进程管理、网络状态、服务管理、启动项、电池、健康检查
  • 桌面集成：系统托盘、开机自启、主题切换

数据模型预留但未实现

详细对比分析

fileterm

相似点：Tauri + React + Rust、文件管理、编辑器、终端、传输任务中心

差异化：偏远程运维（SSH/SFTP），不覆盖知识页面和项目运行

值得借鉴：

  • 终端目录与文件面板联动
  • 命令模板系统
  • 传输任务中心（进度、暂停、恢复）
  • 清晰的领域分层架构
  • 签名更新与多平台发布流程

termul

相似点：项目工作区、终端、代码编辑、文件树、Web 预览

差异化：开发工具属性强，文件资料管理弱

值得借鉴：

  • 分屏工作区布局（编辑器 + 终端 + 预览并排）
  • 持久会话恢复（工作区状态快照）
  • 全局命令面板（Ctrl+K 统一入口）
  • 自定义快捷键系统
  • Git 面板集成

Xplorer

相似点：Tauri 文件管理器、终端、Git、预览、搜索

差异化：next 分支仍标注非生产就绪，主分支架构老旧

值得借鉴：

  • 多标签和分栏文件浏览
  • 丰富的文件预览（PDF、Office、视频、压缩包）
  • 语义搜索集成
  • 扩展市场 + 沙箱插件机制
  • Playwright UI 自动化测试

FilePilot

相似点：本地索引、标签、搜索、批处理、回收站

差异化：Python/PySide 技术栈，不涉及编辑器和终端

值得借鉴：

  • 重复文件检测（哈希 + 相似度）
  • 增量索引机制
  • 保存搜索与智能集合
  • 批量重命名预览
  • 操作历史与撤销
  • OCR 与本地模型接入

Filegraph

相似点：文件、笔记、代码、终端统一工作区

差异化：仓库已归档，仅作设计参考

值得借鉴：

  • 双向链接与反向链接
  • 关系图谱可视化
  • 空间画布（Canvas）
  • 统一文件预览层
  • Agent 工具注册机制

关键结论：没有发现一个项目同时覆盖 Orange 的全部范围。你的差异化恰恰是 Windows 本地文件工作台 + 知识页面 + 开发项目运行 + 系统工具 的融合定位。

当前缺口与风险

P0：产品闭环缺失

  • 标签与资源关系：数据库已有表结构，业务层未落地，无法实现文件、页面、项目的互相关联
  • 统一命令面板：缺少 Ctrl+K 全局入口，高频操作依赖鼠标导航
  • 项目级 Git 工作流：已有代码编辑和终端，但缺文件差异、暂存、提交、分支切换
  • 统一工作区状态：无法保存和恢复项目打开的文件、终端标签、运行任务、面板尺寸

P1：核心竞争力待增强

  • 分屏与多标签工作区：代码、页面、终端、预览无法并排显示
  • 文件智能整理：缺重复检测、批量重命名预览、保存搜索、操作历史
  • 更多文件预览：PDF、Office、CSV、音视频、压缩包预览缺失
  • 任务与资源联动：任务无法关联页面、文件、项目，运行失败无法自动生成待办

P2：工程化与质量

  • Vitest 配置只匹配 src/**/*.test.ts，遗漏 .test.mjs 和 .test.tsx
  • 缺少桌面 UI 端到端测试（Playwright / tauri-driver）
  • 前端无 ESLint/格式化门禁、覆盖率报告
  • CI 无安装包构建、签名、发布和安装验证
  • Tauri 文件访问权限范围过宽（** 全局读权限）
  • 根目录缺少独立 LICENSE 文件
  • 深度依赖 Windows 特性，无跨平台降级策略

三种演进方案

方案 核心方向 优点 风险
A：开发者工作台 Git、分屏、命令面板、工作区恢复、调试运行 与现有项目运行和终端能力衔接最好，定位清晰 文件知识管理差异化利用不足
B：本地知识工作台 标签、双链、关系图、OCR、语义搜索、智能整理 差异化强，文件与页面价值提升明显 索引、解析和 AI 容易扩大范围
C：统一个人工作台 先做统一资源模型，再逐步加入 A、B 的核心能力 最符合当前产品形态，长期扩展性最好 必须控制第一阶段范围，避免继续堆功能

推荐方案 C，但采用 "A 优先、B 跟进" 的实施顺序。

推荐实施路线

第一阶段：统一入口（当前启动）

目标：让现有功能从"多个模块"变成"一个工作台"

  • ✅ 全局命令面板（Ctrl+K）
  • ✅ 标签、收藏和资源关联
  • ✅ 统一最近使用记录
  • ✅ 项目工作区状态恢复
  • ✅ Git 状态、差异和基础提交
  • ✅ 修复测试匹配，建立 UI 冒烟测试

预计工期：2-3 周 | 风险：低，全部为增量功能

第二阶段：统一工作流

  • 分屏与多标签布局
  • 终端、文件树和运行目录联动
  • 项目任务与文件、页面关联
  • 保存搜索和智能集合
  • 重复文件检测、批量重命名预览、操作撤销
  • PDF、Office、CSV 和压缩包预览

第三阶段：可扩展能力

  • 受控插件接口
  • 本地 OCR 和内容提取
  • 可选的 Ollama/OpenAI 兼容接口
  • 语义搜索与文件问答
  • 安装包签名、自动更新、发布流水线

第一阶段详细任务清单

1. 全局命令面板

  • 前端组件：快捷键监听（Ctrl+K / Cmd+K）、模糊搜索、命令分类
  • 命令注册：打开文件、新建页面、切换项目、运行任务、系统工具、设置跳转
  • 最近使用优先级排序

2. 标签与资源关系

  • Rust 服务层：tags CRUD、resource_tags 关联、resource_relations 双向关系
  • 前端 UI：标签输入、标签筛选、关系图可视化（可选）
  • 迁移脚本：确保表结构与索引完整

3. 统一最近使用

  • 数据模型：recent_items 表，记录资源类型、ID、访问时间、访问频率
  • 自动记录：打开文件、编辑页面、切换项目时触发
  • 命令面板集成：最近项优先展示

4. 项目工作区状态

  • 数据模型：workspace_sessions 表，存储项目 ID、打开文件列表、终端标签、运行任务、面板布局
  • 保存时机：项目关闭、应用退出、定时自动保存
  • 恢复逻辑：项目重新打开时还原状态

5. Git 基础工作流

  • 依赖：git2-rs 或调用本地 git 命令
  • 功能：文件状态（modified/staged/untracked）、差异查看、暂存、提交、分支列表、分支切换
  • UI：项目文件树集成 Git 状态标记、差异对比面板、提交输入框

6. 测试补强

  • 修复 vitest.config.ts：匹配 **/*.test.{ts,tsx,mjs}
  • 增加前端 UI 冒烟测试：Vitest + jsdom 或 Playwright
  • 增加覆盖率报告：vitest --coverage
  • CI 增加覆盖率门禁（可选）

实施原则

  • 增量优先：所有功能均为新增或扩展，不破坏现有模块
  • 数据先行：先完成 Rust 服务层和数据库迁移，再做前端 UI
  • 测试同步：每个功能同步编写单元测试和集成测试
  • 文档更新：README 和用户文档同步更新
  • 小步快跑：每完成一项功能即可提交，保持主分支可用
